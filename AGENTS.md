## Architecture rules

- Feature modules live in `src/features/<modulo>/` (`api.ts` with queryOptions + mutations, plus that module's dialogs/components); routes only compose them. Why: keeps each domain area independently extensible.
- Data access goes through the browser Supabase client with RLS as the security boundary; never trust UI checks alone. Why: permissions are enforced in the database per role.
- Roles live in `public.user_roles` (enum `app_role`), checked via SECURITY DEFINER helpers (`has_role`, `is_staff`, `can_access_processo`); never store roles on `perfis`. Why: prevents privilege escalation.
- Public signup and social sign-in are off; admins create, edit and delete accounts in "Equipe e acessos" through admin-only server functions (`src/features/equipe/usuarios.functions.ts`, caller role checked before using the service client). The `handle_new_user` trigger still creates the profile + `cliente` role, then the function applies the chosen role. Admins cannot change their own role or delete themselves. Why: the office controls who gets access and never locks itself out.
- Client address is stored as separate columns on `clientes` (cep, logradouro, numero, complemento, bairro, cidade, uf); CEP lookup uses the public ViaCEP API from the browser. Why: structured address for petitions without an extra table.
- The Agenda page reads the same `prazos_e_tarefas` query as the Kanban (no separate events table). Why: calendar and task board always stay in sync.
- Client phones live in `clientes.telefones` (jsonb array of `{numero, whatsapp}`, at most one WhatsApp) via helpers in `src/lib/telefone.ts`; the old `telefone` column is deprecated. Why: multiple phones without an extra table.
- A process is displayed by `processoLabel()` (title, falling back to CNJ); `numero_cnj` is optional. Why: cases may exist before distribution.
- Every protected page lives under `src/routes/_authenticated/` (ssr: false gate + sidebar shell); pages use loader `ensureQueryData` + `useSuspenseQuery` with a skeleton `pendingComponent`. Why: consistent auth gating and loading UX.
- Digital-folder files go to the private `pastas-digitais` bucket under `<processo_id>/...`; `arquivo_url` stores the storage path and downloads use short-lived signed URLs. Why: storage policies key off the folder's process id.
- Backend errors are shown through `friendlyError()` in `src/lib/errors.ts`; domain rules (CPF/CNPJ, CNJ, deadline urgency) live in `src/lib/` with tests next to them. Why: one place for messages and testable rules.
- The system name/subtitle (white-label) live in the single-row `public.configuracoes` table (public read, admin-only update) and are read via `marcaQueryOptions()`; routes put `marca` into context in `beforeLoad` so `head()` titles use `tituloPagina()`. Why: each office that buys the system can rename it without code changes.
- Case movements are a dated history in `public.processo_movimentacoes` (date-only `data_movimentacao`, author, RLS via `can_access_processo`; lawyers edit only their own, only admin deletes); the old `processos.andamento` column is deprecated and was backfilled. Date rules live in `src/lib/movimentacoes.ts` and parse dates as local days. Why: a timeline per case, and date-only values must not shift a day in UTC-3.
- Finance lives in `public.transacoes` + `public.categorias_financeiras` (module `src/features/financeiro/`); only admin writes, lawyers only SELECT rows linked to a process they can access (`can_access_processo`). A trigger enforces category type = transaction type and inherits `cliente_id` from the process. Receipts go to the private `comprovantes-financeiros` bucket (`<uuid>/<file>`, read via `can_access_comprovante`). "Atrasado" is also derived in the UI (`statusEfetivo` in `src/lib/financeiro.ts`: pending past due date) and all totals/charts come from that module. Why: one source of truth for money rules and no stale overdue status.
